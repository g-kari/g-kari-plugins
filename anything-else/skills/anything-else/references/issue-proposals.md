# Issue作成案

Issueは現在のセッションとの関連が確認できるものだけを提案する。作成先のリポジトリを確認し、既存Issueの open / closed 両方を検索する。読み取り権限や接続がない場合は、重複確認をしたことにしない。

## 本文テンプレート

```text
タイトル: [今回の作業に直接関連する具体的な未着手タスク]

## 背景・根拠
- セッション中に保留した内容と理由
- 関連Issue／PR／ファイル箇所（確認できたもの）

## 作業内容
- 次の担当者が着手できる具体的な変更

## 受け入れ条件
- 完了したと判断できる観測可能な条件

## 確認方法
- 対象テストや再現・確認の手順

## 重複確認
- 検索済みの既存Issueと、重複しない理由
```

## GitHub CLIのコマンド案

次は形式の例であり、実行しない。OWNER/REPO とタイトル・本文は確認済みの値に置き換え、未確認ならプレースホルダーと明示する。gh が使えない場合は本文だけ提示すればよい。

```bash
gh issue create --repo 'OWNER/REPO' --title '空入力時の回帰テストを追加する' --body-file - <<'ANYTHING_ELSE_ISSUE'
## 背景・根拠
今回の変更で空入力の処理を変更したが、会話中にテスト追加を保留した。

## 作業内容
対象処理に空入力の回帰テストを追加する。

## 受け入れ条件
空入力に対する仕様上の結果をテストで確認できる。

## 確認方法
対象プロジェクトで既存のテスト実行方法を確認して追記する。
ANYTHING_ELSE_ISSUE
```

安全なコマンド案では、引数をシングルクォートする。値に `'` がある場合はシェルの `\'` で済ませず、POSIX shellでは `'"'"'` で区切って表現する。本文にはクォート付きheredocを使い、本文の行と衝突しない区切り文字を選ぶ。機密情報を本文・コマンドに含めず、ラベルや担当者を推測して指定しない。Issue作成、追記、closeは別途の明示的な実行依頼に従う。
